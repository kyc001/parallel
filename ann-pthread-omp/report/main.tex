\section*{摘要}
\addcontentsline{toc}{section}{摘要}

本实验围绕 DEEP100K 上的近似最近邻搜索（ANNS）实现了一个 header-only 的多算法并行框架。系统以 SIMD 距离计算为底层公共内核，在此基础上实现 Flat-SIMD、SQ-SIMD、PQ-SIMD、PQ-FastScan、IVF-SIMD、IVF-PQ-SIMD 与 HNSW 图索引，并分别给出 Pthread 与 OpenMP 版本。Pthread 侧实现了 static、dynamic 与 pool 三类调度；并行粒度覆盖 query 级并行（inter-query）与单 query 内部的 base/list 划分（intra-query）。实验在本地 i9-13900H（x86 AVX2）和鲲鹏 920（ARM NEON）两个平台完成。两个平台使用相同代码（\texttt{unified\_bench.cc}），产出 319 组等价实验矩阵；本地额外 45 组 IVF-PQ global 构建模式结果为补充数据。针对初稿中 PQ/IVF-PQ recall 偏低的问题，额外补充了高召回参数诊断、重跑清单、时钟分析与汇编分析。

实验结果显示，query 级并行是本数据集和批量查询场景下最稳健的并行粒度。Flat、SQ、FastScan、IVF 的本地高召回最优延迟分别为 298.95、86.53、125.81 与 104.67 $\mu$s；PQ 在 $p=1000$ 时达到 0.98335 recall、136.47 $\mu$s，IVF-PQ local 在 \texttt{nprobe=4,p=1000} 时达到 0.95945 recall、61.32 $\mu$s。Pthread dynamic 在多数规则扫描类算法上表现最好，Pthread pool 在 IVF inter-query 上略优，说明线程创建开销、尾部不均衡与 inverted list 不均匀性都会影响最终表现。HNSW 的内部并行更复杂：原始 baseline 延迟最低但召回较低，多入口点和边划分能提升召回，但同步和路径依赖使其不适合作为默认最快路径。

\noindent\textbf{关键词：} ANN，Pthread，OpenMP，SIMD，IVF，IVF-PQ，HNSW，FastScan，负载均衡

\section{问题定义与目标}

给定基向量集合
\[
X=\{x_1,x_2,\ldots,x_N\}\subset\mathbb{R}^d
\]
以及查询向量 $q\in\mathbb{R}^d$，$k$ 近邻搜索希望找到 $X$ 中与 $q$ 距离最近的 $k$ 个向量。本文使用的距离形式沿用课程框架中的内积距离：
\[
\delta(x,q)=1-\sum_{i=1}^{d}x_iq_i .
\]
近似最近邻搜索不要求每次完全返回真实 top-$k$，因此用 Recall@$k$ 衡量准确率：
\[
\mathrm{Recall@}k = \frac{|KNN(q)\cap KANN(q)|}{k}.
\]

本次作业的核心目标不是单独做 SIMD，而是在已经具备 SIMD 距离内核的基础上，系统实现 Pthread / OpenMP 多线程并行，并从以下方面进行评估：
\begin{enumerate}
  \item 对 Flat、SQ、PQ、FastScan、IVF、IVF-PQ 与 HNSW 进行统一实现和测试；
  \item 比较 Pthread static、dynamic、pool 与 OpenMP 的任务划分和调度开销；
  \item 比较 inter-query 与 intra-query 两种并行粒度；
  \item 分析线程数、负载均衡、top-$k$ reduce、cache / 内存访问和负优化现象；
  \item 对 IVF / IVF-PQ 给出 \texttt{nprobe} 与构建模式对 latency-recall 的影响。
\end{enumerate}

\subsection{并行框架}

本文实现了两类并行粒度。

\textbf{Inter-query 并行。} 每个线程处理一批完整 query。线程间不共享搜索状态，只写入结果数组中的不同位置，因此同步开销最低。对于批量查询，inter-query 通常能获得最好的吞吐和延迟表现。

\textbf{Intra-query 并行。} 对单条 query，将 base 向量集合、候选集合或 IVF inverted list 分给多个线程。每个线程维护局部 top-$k$ 或 top-$p$ 堆，最后由主线程 merge。这种方式适合单 query 延迟优化，但会引入局部堆维护、线程同步和 top-$k$ reduce 成本。

Pthread 侧实现三种调度方式：
\begin{itemize}
  \item static：静态等分任务，适合 Flat 这类计算量规则的扫描；
  \item dynamic：用原子计数器动态抢任务，适合 query 耗时或 list 长度不均匀的场景；
  \item pool：预创建线程池和任务队列，减少反复创建 / 销毁线程的开销。
\end{itemize}

OpenMP 侧主要使用 \texttt{parallel for}，query 级循环使用 dynamic schedule，base/list 扫描使用局部堆加串行 merge。

\section{并行原理分析}

本节从系统层面分析多线程并行的核心原理，为后续实验结果提供理论基础。

\subsection{线程生命周期与同步开销}

Pthread 创建线程需要分配栈空间、设置 TLS（Thread-Local Storage）并调用 \texttt{clone} 系统调用。在 Linux 上，单次 \texttt{pthread\_create} 的典型开销为 10--50 $\mu$s。如果每个 query 都创建/销毁线程，线程管理开销会成为短查询场景的瓶颈。

本文的三种调度策略对线程生命周期的处理不同：

\begin{itemize}
  \item \textbf{Static / Dynamic}：每次调用并行搜索时创建 $T$ 个线程，等待 \texttt{pthread\_join} 后销毁。线程创建开销为 $O(T)$，但每个线程处理的任务量为 $O(Q/T)$（$Q$ 为 query 数），因此当 $Q$ 足够大时，创建开销可被摊薄。
  \item \textbf{Pool}：线程池在初始化时创建 $T$ 个线程，通过 \texttt{pthread\_mutex\_t} + \texttt{pthread\_cond\_t} 实现任务队列。线程在整个程序生命周期内复用，避免反复创建/销毁。但每次任务分发需要 \texttt{mutex\_lock} + \texttt{cond\_signal} + \texttt{mutex\_unlock}，引入额外同步开销。
\end{itemize}

\subsection{Cache 行为分析}

DEEP100K 的 base 向量为 100K $\times$ 96 维 $\times$ 4 字节 = 36.8 MB，远超典型 L3 缓存（i9-13900H 的 L3 为 24 MB，鲲鹏 920 的 L3 为 32 MB）。因此全量扫描必然产生大量 cache miss。

\textbf{Inter-query 并行}下，每个线程独立处理一条 query，需要遍历全部 base 向量。多线程同时访问相同的 base 数据（只读），可以利用 L3 共享缓存。但当线程数增加时，L3 带宽成为瓶颈。

\textbf{Intra-query 并行}下，多个线程同时处理同一条 query 的不同 base 子集。每个线程访问的 base 片段不同，L1/L2 缓存利用率更高（因为每个线程的工作集更小）。但需要额外的局部堆维护和最终 merge 操作。

\subsection{内存带宽瓶颈}

Flat 全扫描需要读取 36.8 MB base 数据。在 DDR4-3200 双通道下，理论带宽约为 51.2 GB/s，但实际有效带宽通常为 60--80\%。对于单线程，内存带宽已经足够；但当线程数增加到 8--16 时，多线程同时读取 base 数据会迅速饱和内存带宽。

这就是为什么 Flat 从 8 线程到 16 线程的加速比明显下降：不是计算能力不足，而是内存带宽成为瓶颈。PQ 和 FastScan 通过量化压缩（每个 base 从 384 字节压缩到 8--12 字节），显著减少了内存读取量，因此在高线程数下仍能保持较好扩展性。

\subsection{负载均衡分析}

负载均衡是多线程性能的关键因素。理想情况下，每个线程的工作量应该相等，这样所有线程同时完成，总时间等于单线程时间除以线程数。

\textbf{Static 调度}将任务均匀分配给各线程。当任务量规则（如 Flat 的 base 扫描）时效果好；但当任务量不均匀（如 IVF 的不同 inverted list 长度差异大）时，某些线程会提前空闲，等待最慢的线程完成。

\textbf{Dynamic 调度}通过原子计数器实现动态任务分配。每个线程完成当前任务后立即获取下一个任务，自然适应任务量差异。代价是每次获取任务需要一次原子操作（\texttt{fetch\_add}），但在任务粒度足够大时，这个开销可以忽略。

\subsection{False Sharing 与缓存行冲突}

False sharing 发生在不同线程写入同一缓存行（通常 64 字节）的不同位置时。即使逻辑上不冲突，硬件层面的缓存一致性协议（MESI）仍会导致缓存行在 core 间反复弹跳，严重降低性能。

在 intra-query 并行中，每个线程维护局部 top-$k$ 堆。如果这些堆在内存中紧邻存放，堆的更新操作可能触发 false sharing。解决方案是让每个线程的堆分配在独立的缓存行对齐内存区域。

\subsection{并行归约与 Top-$k$ Merge}

Intra-query 并行的最后一步是将各线程的局部 top-$k$ 堆合并为全局 top-$k$。这是一个归约操作，可以用多种方式实现：

\textbf{串行 Merge}：主线程依次合并各线程的堆。时间复杂度为 $O(T \cdot k \log k)$，其中 $T$ 为线程数。

\textbf{树形归约}：类似蝴蝶网络，线程两两合并，$\log T$ 轮完成。每轮合并 $k$ 个元素，总时间 $O(k \log T)$。但需要额外的同步屏障。

\section{算法实现}

\subsection{Flat-SIMD}

Flat 是精确全量扫描。每个 query 需要访问全部 $N$ 个 base 向量并维护 top-$k$ 堆。距离计算复用 \path{simd/flat_scan_simd.h}，在 x86 上使用 AVX2，在 ARM 上保留 NEON 路径。

Flat 的计算量规则，因此理论上 static 划分也应较强。但在本机 Windows 混合核调度环境下，dynamic query 抢任务可以减轻尾部等待和系统噪声，实际取得最优结果。Intra-query 版本需要每个线程维护局部堆并在单 query 结束后 merge，因此固定开销显著。

\subsection{SQ-SIMD}

SQ 将 float32 向量逐维量化为 uint8，查询阶段采用两阶段流程：第一阶段在 uint8 空间快速粗排得到 top-$p$ 候选，第二阶段对候选使用原始 float32 内积进行 rerank。本文在 Pthread 与 OpenMP 中都实现了 query 级整条流水线并行，以及单 query 内粗排阶段 base 划分并行。由于精排候选集合较小，精排阶段主要保持单线程执行，避免额外同步开销。

\subsection{PQ-SIMD 与 FastScan}

PQ 将 96 维向量切分为 $M=8$ 个子空间，每个子空间训练 256 个中心。查询时对每个子空间构建 LUT，并用 ADC 对 base 的 PQ code 查表累加。Pthread / OpenMP 版本分别对 query 循环或 base code 扫描进行并行化。

FastScan 是 PQ 的进一步压缩实现，使用 4-bit code 和更小 LUT，将查表过程转为寄存器内 shuffle。FastScan 的 ADC 阶段更偏 memory-bound，线程数过多可能更早触及带宽上限。因此本文重点比较 inter-query 与 intra-query 的差异，并在报告中保留负优化结果。

\subsection{IVF-SIMD}

IVF 在离线阶段用 KMeans 将 base 聚为 \texttt{nlist} 个簇。查询时先计算 query 到各簇中心的距离，选择最近的 \texttt{nprobe} 个簇，再扫描这些 inverted list 并用 SIMD 原始距离 rerank。实现中保留簇内连续存储信息，减少精排阶段的随机访问。

\begin{itemize}
  \item IVF-SIMD baseline；
  \item query 级 Pthread / OpenMP 并行；
  \item 单 query 内按 list 或候选段划分并行；
  \item \texttt{nprobe} sweep，用于展示 latency-recall trade-off。
\end{itemize}

\subsection{IVF-PQ-SIMD}

IVF-PQ 将 IVF 的候选缩减与 PQ 的压缩距离计算叠加。本文实现两种构建方式：
\begin{enumerate}
  \item global-PQ-first：先对所有 base 做全局 PQ 编码，再构建 IVF；
  \item IVF-local-PQ：先构建 IVF，再在簇内维护局部 PQ 编码。
\end{enumerate}

查询时先 IVF 粗排选择 \texttt{nprobe} 个簇，再在选中簇内用 PQ ADC 得到候选并 rerank。由于 PQ 显著减少单次距离计算量，IVF-PQ 更容易转为内存访问和调度开销主导，线程数并非越多越好。

\subsection{HNSW 进阶}

HNSW 基于 hnswlib 实现。本文不修改 hnswlib 源码，而是通过封装访问底层图结构，实现以下并行策略：
\begin{itemize}
  \item baseline：原始 \texttt{searchKnn}；
  \item 多入口点并行：多个线程从不同入口出发，最后 merge top-$k$；
  \item 边划分并行：并行计算当前节点邻居距离；
  \item Layer0 点划分：按节点 ID 范围切分底层图扫描；
  \item IVF-HNSW 嵌套：先 IVF 粗排，再并行搜索多个小 HNSW。
\end{itemize}
图搜索路径依赖强，内部并行容易被同步和候选队列更新开销抵消，因此 HNSW 部分重点如实分析正优化与负优化。

\section{综合讨论}

\subsection{并行粒度选择的本质原因}

实验结果一致表明 inter-query 优于 intra-query。这不仅是本数据集的特性，而是反映了批量搜索场景下的系统层面规律：

\begin{enumerate}
  \item \textbf{任务独立性}：Inter-query 下各 query 搜索完全独立，无需共享状态，同步开销为零。Intra-query 下多线程共享同一条 query 的搜索过程，需要局部堆和 merge 操作。
  \item \textbf{SIMD 复用}：Inter-query 自然复用已有的 SIMD 距离内核，每个线程调用相同的串行搜索函数。Intra-query 需要修改搜索函数以支持部分 base 扫描，增加了代码复杂度。
  \item \textbf{Cache 利用}：Inter-query 下每个线程遍历全部 base，L3 共享缓存命中率高。Intra-query 下每个线程访问 base 的不同片段，L1/L2 命中率更高但 L3 利用率下降。
  \item \textbf{负载均衡}：Inter-query 通过 dynamic 调度自然适应 query 间耗时差异。Intra-query 的负载均衡取决于 base 向量分布，更难预测。
\end{enumerate}

\subsection{调度策略选择依据}

三种 Pthread 调度策略各有适用场景：

\textbf{Static}适合任务量规则、可预测的场景。Flat 的 base 扫描计算量均匀，static 划分开销最低。但在 Windows 混合核环境下，系统调度噪声会导致尾部线程延迟，实际表现不如 dynamic。

\textbf{Dynamic}适合任务量不均匀或系统噪声较大的场景。通过原子计数器实现的动态任务分配，让快线程自然多做工作，避免慢线程成为瓶颈。代价是每次 \texttt{fetch\_add} 引入一次原子操作，但在任务粒度足够大时可忽略。

\textbf{Pool}适合需要频繁创建/销毁线程的场景。线程池通过 \texttt{mutex+cond} 实现任务队列，线程在整个程序生命周期内复用。IVF 的 inverted list 扫描场景下，pool 略优于其他策略，因为索引对象的访问模式更稳定。

\subsection{算法特性与瓶颈分析}

不同算法的并行扩展性差异显著，根本原因在于计算特性不同：

\begin{itemize}
  \item \textbf{Flat / SQ}：compute-bound，每个 base 需要 96 次浮点乘加。内存带宽在 8 线程后成为瓶颈，16 线程加速比下降。
  \item \textbf{PQ / FastScan}：memory-bound，每个 base 只需 8--12 字节查表。线程数增加时仍能保持较好扩展性，因为内存读取量小。
  \item \textbf{IVF}：混合型，粗排阶段 compute-bound（计算到质心距离），精排阶段 memory-bound（扫描 inverted list）。Pool 调度在精排阶段略优。
  \item \textbf{IVF-PQ}：memory-bound，PQ 压缩后的 inverted list 极小，搜索几乎完全受内存访问限制。高线程数下延迟接近常数。
  \item \textbf{HNSW}：同步-bound，图搜索的路径依赖导致并行化困难。多入口点和边划分更多是为了提升 recall，而非降低延迟。
\end{itemize}

\subsection{跨平台架构差异}

鲲鹏 ARM NEON 与 x86 AVX2 的延迟比值在 1.4--3.9$\times$ 之间。这个差异来自三个层面：

\begin{enumerate}
  \item \textbf{SIMD 宽度}：AVX2 为 256-bit，NEON 为 128-bit。对于 float32 乘加，AVX2 每周期处理 8 个，NEON 处理 4 个。理论加速比应为 2$\times$，但实际差异受其他因素影响。
  \item \textbf{单核频率}：i9-13900H 的 P-core 频率（5.4 GHz boost）高于鲲鹏 920（2.6 GHz）。频率差异约 2$\times$，与 SIMD 宽度差异叠加后，理论加速比约 4$\times$。
  \item \textbf{内存子系统}：i9-13900H 的 DDR5 带宽高于鲲鹏 920 的 DDR4。对于 memory-bound 算法（PQ、FastScan），内存带宽差异的影响大于计算能力差异。
\end{enumerate}

FastScan 的 ARM/x86 比值最低（1.4$\times$），说明其瓶颈在查表和访存，而非浮点计算。Flat 的比值最高（3.1$\times$），接近理论计算能力差异。

\section{结论与后续工作}

\subsection{主要结论}

\begin{enumerate}
  \item \textbf{Inter-query 并行是最稳健的并行粒度}：在批量 query 场景中，query 级并行避免了局部 top-$k$ merge 和频繁同步，能自然复用 SIMD 内核，取得最优性能。
  \item \textbf{Pthread dynamic 在多数场景下表现最好}：原子计数器的动态任务分配适应了 query 耗时差异和系统噪声，代价可忽略。
  \item \textbf{内存带宽是高线程数的瓶颈}：Flat 和 SQ 在 8 线程后加速比下降，因为 base 数据读取饱和了内存带宽。PQ 和 FastScan 通过量化压缩缓解了这个问题。
  \item \textbf{HNSW 并行化的核心目标是 recall 而非速度}：多入口点和边划分提升 recall，但同步开销限制了延迟降低。
  \item \textbf{跨平台差异主要由 SIMD 宽度和频率决定}：memory-bound 算法的跨平台差异小于 compute-bound 算法。
\end{enumerate}

\subsection{后续工作}

\begin{enumerate}
  \item \textbf{$p$ sweep 系统化}：对 SQ/PQ/FastScan 做更系统的 $p$ sweep，形成完整的 latency-recall 曲线，为实际部署提供参数选择依据。
  \item \textbf{HNSW 无锁优化}：尝试无锁 visited 标记（如 atomic bitmap）和更细粒度的共享候选队列，降低图搜索并行的同步成本。
  \item \textbf{NUMA 感知}：在鲲鹏等多 socket 平台上，考虑 NUMA 拓扑对内存访问延迟的影响，将线程绑定到最近的内存节点。
  \item \textbf{混合并行}：结合 inter-query 和 intra-query 的优势，例如在 query 数量不足时自动切换到 intra-query 模式。
  \item \textbf{GPU 加速}：将 SIMD 距离计算扩展为 CUDA/OpenCL 内核，利用 GPU 的大规模并行能力进一步降低延迟。
\end{enumerate}
