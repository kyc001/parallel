\section*{摘要}
\addcontentsline{toc}{section}{摘要}

本实验在前两次 ANN 实验已有的 SIMD 距离内核、IVF-PQ 和 HNSW 结构基础上，将搜索任务迁移到 MPI 多进程环境，并在每个 MPI rank 内继续使用 OpenMP 做进程内并行。程序采用统一入口 \code{main.cc}，支持四种搜索模式：IVF-PQ、分块 HNSW、IVF+HNSW 嵌套索引，以及 HNSW-on-HNSW 分层图索引。MPI 层负责 base 向量划分、query 广播、候选集 gather 和 rank 0 的 top-$k$ 合并；OpenMP 层负责本地倒排表、HNSW 块或候选块之间的并行搜索。

实验使用 DEEP100K 数据集，距离度量为内积距离，统一评价 Recall@10、平均单 query 延迟、本地最慢 rank 搜索时间以及通信与合并开销。报告给出 Windows 本地 MS-MPI、鲲鹏服务器直接 \code{mpiexec} 和 PBS \code{qsub} 三条路径的同参数结果。结果表明：相同参数下两平台 Recall 完全一致；在 \code{np=8, threads=2, query=2000} 的全量验证规模中，通信与 merge 占比始终小于约 1.4\%，主要瓶颈仍在各 rank 的本地 ANN 搜索。图索引方面，block-HNSW 达到 Recall@10=1.00000，HNSW-on-HNSW 达到 Recall@10=0.99995；HNSW-on-HNSW 在全 block 探测配置下保持接近满召回但延迟较大，体现了典型的 recall-latency trade-off。

\noindent\textbf{关键词：} ANN；MPI；OpenMP；IVF-PQ；HNSW；HNSW-on-HNSW；负载均衡；通信开销

\section{问题定义与实验目标}

给定基向量集合
\[
X=\{x_0,x_1,\ldots,x_{N-1}\}, \quad x_i\in \mathbb{R}^{96},
\]
以及 query 向量 $q$，ANN 搜索返回与 $q$ 最接近的 $k$ 个候选。本实验沿用前两次 ANN 作业的内积距离：
\[
d(x,q)=1-\sum_{j=0}^{d-1}x_jq_j.
\]
Recall@$k$ 定义为返回集合与 ground truth top-$k$ 的交集比例：
\[
\mathrm{Recall@}k=\frac{|KNN(q)\cap KANN(q)|}{k}.
\]

与 Pthread/OpenMP 实验不同，本次实验关注的不是单机线程如何分配，而是多进程之间如何划分数据、如何通信、如何将每个 rank 的局部结果归并为全局 top-$k$。因此报告重点围绕以下问题展开：
\begin{enumerate}
  \item base data 如何划分到不同 MPI 进程，且尽量保持负载均衡；
  \item query 如何广播，各 rank 如何维护本地索引并返回局部 top-$k$；
  \item rank 0 的 gather/merge 开销相对本地搜索是否显著；
  \item MPI 与 OpenMP 如何组合，进程间并行和进程内并行的边界在哪里；
  \item IVF-PQ 与三类图索引方案在 recall-latency 上有什么差异；
  \item 同一份代码在 Windows 本地和鲲鹏服务器上是否可复现。
\end{enumerate}

代码与脚本均放在 \code{ann-mpi/} 目录下。正式提交入口为 \code{main.cc} 与 \code{qsub_mpi.sh}；报告中引用的运行记录分别为本地交叉验证日志、鲲鹏直跑日志和鲲鹏 PBS 日志，均已保存在 \code{results/} 目录。

\subsection{负载划分}

代码中使用 \code{PartitionRange(n, rank, world_size)} 对 base 向量做连续分块。设进程数为 $P$，则每个 rank 得到
\[
\left\lfloor \frac{N}{P}\right\rfloor
\quad\text{或}\quad
\left\lceil \frac{N}{P}\right\rceil
\]
个向量，最大只差 1。连续划分的优点是实现简单、传输时可直接使用 \code{MPI_Scatterv} 的 displacement，同时每个 rank 的 \code{local_base} 连续存储，有利于本地 cache locality。缺点是如果数据分布本身有明显偏斜，某些 rank 的搜索路径可能更长；因此程序额外打印 \code{max local search latency (us)}，用最慢 rank 的搜索时间衡量负载尾部。

\begin{lstlisting}[language=C++]
Range PartitionRange(size_t n, int rank, int world_size) {
    const size_t base = n / world_size;
    const size_t extra = n % world_size;
    const size_t begin = rank * base + std::min<size_t>(rank, extra);
    const size_t count = base + (rank < extra ? 1 : 0);
    return {begin, begin + count};
}
\end{lstlisting}

\subsection{局部搜索与全局合并}

每个 rank 的局部搜索结果以小顶堆形式保存。为了跨进程传输，程序将每个 query 的 top-$k$ 打包成两个定长数组：距离 \code{float} 和全局 id \code{uint64_t}。rank 0 收到所有 rank 的候选后，对每个 query 扫描 $P\times k$ 个候选并维护全局 top-$k$ 堆。因此 merge 的复杂度近似为
\[
O(QPk\log k),
\]
其中 $Q$ 是 query 数。与本地搜索的 IVF 或 HNSW 访问相比，当 $P$ 和 $k$ 不大时，这部分开销很小。正式全量实验中 $P=8,k=10,Q=2000$，每个 rank 发送约 $Qk(4+8)\approx 234$ KiB 候选数据，query 广播约 $Qd\cdot4\approx 750$ KiB，因此通信量仍小于本地索引搜索的访存量。

\subsection{IVF-PQ 的 MPI 迁移}

IVF-PQ 是从上一阶段多线程版本迁移到 MPI 的基础方案。多线程版本中，一个进程维护完整索引；MPI 版本中，每个 rank 只维护本地 shard 的 inverted lists。query 被广播到所有进程后，各 rank 只在本地 list 中搜索，返回局部 top-$k$。由于每个 rank 只看到一部分 base data，最终的 top-$k$ 必须由 rank 0 对所有局部结果进行全局合并。

进程内仍复用 OpenMP inter-query 并行：当 query 批量足够大时，不同线程处理不同 query，写入不同结果槽，几乎不需要同步。这一点延续了前一次 Pthread/OpenMP 实验中“inter-query 粒度更稳健”的结论。

\textbf{方案 A：IVF+HNSW。}每个 rank 内先建立 IVF 粗聚类，随后在每个簇中单独建立 HNSW。搜索阶段先按 query 与质心距离选择 \code{nprobe} 个簇，再在这些簇的 HNSW 内搜索。它的优点是能避免搜索所有局部向量；缺点是召回依赖簇选择，若 ground truth 所在簇未被探测，则后续 HNSW 再精确也无法恢复。

\textbf{方案 B：分块 HNSW。}MPI 本身已经把 base 划分成多个 shard，因此每个 rank 的 HNSW 可以视为一个独立 block graph。所有 rank 并行搜索自己的图，rank 0 再合并结果。该方案实现直接、召回较高，但每个局部 HNSW 的搜索路径具有串行依赖，OpenMP 只能在多入口或多 query 层面分摊，不能把单条贪心路径线性拆开。

\textbf{方案 C：HNSW-on-HNSW。}本实验进一步实现了分层图：每个 rank 把本地 base 分成多个 block，先计算 block centroid 并建立 top-level HNSW；每个 block 内再建立 bottom-level HNSW。搜索时先在 centroid graph 上选择若干 block，再并行搜索被选中的 block graph。它能表达“图上再建图”的组合策略；当 \code{nprobe_blocks} 取满 16 时，全量实验 Recall@10 达到 0.99995，但因为实际搜索了所有 block，延迟明显上升。

\subsection{混合并行边界}

本实验的混合并行不是简单地同时打开 MPI 和 OpenMP，而是明确划分职责：
\begin{itemize}
  \item MPI 层：base shard 分配、query 广播、候选 gather、最慢 rank 计时归约、rank 0 top-$k$ merge；
  \item OpenMP 层：rank 内 query/list/block 级并行，避免跨进程共享状态；
  \item 索引层：每个 rank 独立构建本地 IVF-PQ 或 HNSW，不在在线阶段跨进程访问远端索引。
\end{itemize}

这种边界使程序比较容易在 Windows MS-MPI 和鲲鹏 OpenMPI/MPI 环境中复现。它也限制了通信复杂度：在线阶段只有一次 query broadcast 和一次候选 gather，没有在 HNSW 搜索路径中进行细粒度跨 rank 通信。

\subsection{在线阶段伪代码}

为了说明 MPI 代码的控制流，下面给出一次批量查询的伪代码。索引构建发生在计时前；报告中的 online latency 从 query broadcast 前的 barrier 之后开始计时，直到 rank 0 完成 merge 和 recall 计算前结束。

\begin{lstlisting}[language=C++]
// rank 0 loads base/query/ground truth, then broadcasts dimensions.
range = PartitionRange(base_n, rank, world_size);
MPI_Scatterv(root_base, counts, displs, MPI_FLOAT, local_base);

index = BuildLocalIndex(local_base, mode);

MPI_Barrier(MPI_COMM_WORLD);
phase_begin = MPI_Wtime();
MPI_Bcast(queries, query_n * dim, MPI_FLOAT, 0, MPI_COMM_WORLD);

search_begin = MPI_Wtime();
local_topk = SearchLocal(index, queries, nthreads);
search_us = MPI_Wtime() - search_begin;

PackCandidates(local_topk, range.begin, local_distances, local_ids);
MPI_Gather(local_distances, all_distances, 0, MPI_COMM_WORLD);
MPI_Gather(local_ids, all_ids, 0, MPI_COMM_WORLD);
MPI_Reduce(search_us, max_search_us, MPI_MAX, 0, MPI_COMM_WORLD);

if (rank == 0) {
    merged = MergeGatheredCandidates(all_distances, all_ids);
    total_us = MPI_Wtime() - phase_begin;
    comm_merge_us = total_us - max_search_us;
    recall = RecallAtK(merged, ground_truth);
}
\end{lstlisting}

这里使用 \code{MPI_Reduce} 的 \code{MPI_MAX} 而不是平均值，是因为一次分布式查询必须等最慢 rank 完成本地搜索后才能合并。因此总延迟应与最慢 rank 的搜索时间对齐，\code{comm_merge_us} 才能表示“除了最慢本地搜索以外的剩余开销”。如果用平均搜索时间，会把负载不均衡误计入通信开销。

\subsection{Recall-latency 分析}

IVF-PQ 与 IVF+HNSW 都使用“先筛选、再精排或图搜索”的思路，因此延迟较低但召回略低。本地 Windows 上 block-HNSW 为 188.02760 $\mu$s/query，是四种模式中最快的；IVF+HNSW 的 Recall@10 为 0.96450，略低于 block-HNSW 和 HNSW-on-HNSW。IVF-PQ 的 Recall@10 为 0.96515，延迟在 Windows 上为 297.55775 $\mu$s/query，在鲲鹏 PBS 上为 498.40915 $\mu$s/query。

block-HNSW 在三条路径上都达到 Recall@10=1.00000。Windows 上该模式延迟最低；鲲鹏 direct 和 PBS 上约为 0.8 ms/query，明显慢于 Windows，但仍保持满召回。这说明分块图索引是高召回和较低实现复杂度之间较好的折中，同时也对不同平台的图访问、优先队列和分支预测更敏感。

HNSW-on-HNSW 达到 Recall@10=0.99995，但在鲲鹏上延迟达到 2.46--2.65 ms/query。原因在于本报告为了验证方案 C 的召回上限，将 \code{nprobe_blocks=16} 设置为探测所有 block；top-level HNSW 选块之后，bottom-level 搜索仍覆盖全部局部 block，因此它更适合作为“高召回但高搜索代价”的对照点。若实际追求低延迟，应进一步 sweep \code{nprobe_blocks}，观察从少量 block 到全 block 的召回曲线。

\subsection{平台差异}

Windows 与鲲鹏的 Recall 完全一致，说明浮点距离、候选 id 偏移和 rank 0 merge 逻辑在两个平台上保持一致。延迟上，Windows 本地在四种模式中整体更快，鲲鹏 direct/PBS 的图索引模式更慢。这个现象说明不同算法对硬件的敏感点不同：IVF-PQ 更依赖顺序数组访问、PQ 查表和 rerank；HNSW 更依赖图访问、优先队列和分支路径。PBS 与 direct 的差异还受到队列节点位置和共享负载影响，因此报告同时保留两份服务器日志，而不只引用一次运行。

\subsection{结果可信性检查}

本次结果首先看正确性，再看速度。四种模式在 Windows、鲲鹏 direct 和 PBS 中的 Recall 完全复现，尤其是 IVF-PQ 的 0.96515、IVF+HNSW 的 0.96450、block-HNSW 的 1.00000 以及 HNSW-on-HNSW 的 0.99995 在三条路径中一致，这说明候选 id 的全局偏移、跨 rank gather 顺序和 top-$k$ merge 没有平台相关错误。

其次看计时拆分。所有记录中都有
\[
\text{latency}\approx \text{max local search}+\text{comm+merge}.
\]
例如 Windows IVF-PQ 中 $295.03885+2.51890=297.55775$，与总延迟完全对齐；鲲鹏 PBS 的 HNSW-on-HNSW 中 $2462.41915+2.93446=2465.35361$，与总延迟完全对齐。这说明 \code{comm+merge latency} 的计算口径稳定，不是事后人为估计。

最后看双平台解释。PBS 和 direct 的延迟并不完全相同，但 Recall 一致，说明性能波动主要来自服务器环境和运行路径，而不是算法逻辑改变。报告中的全量实验固定在 \code{np=8}，因此仍不是完整强扩展实验；在“问题与改进方向”中单独说明还需要补充 \code{np=1,2,4,8} 的多进程 sweep。

\section{问题与改进方向}

\textbf{更多进程数的扩展性。}本报告以 \code{np=8} 做双平台全量验证，已经能证明 MPI 数据流、合并逻辑和 PBS 提交流程正确。但要更系统地分析扩展性，还应补充 \code{np=1,2,4,8} 的 sweep，并在服务器负载较低时重复多次取中位数。预计当进程数增大时，本地搜索时间会下降，但候选 gather 和 rank 0 merge 会逐渐变得更明显。

\textbf{HNSW-on-HNSW 参数。}\code{nprobe_blocks=16} 是偏向高召回的配置，相当于在 top-level graph 之后仍搜索全部 block。后续可以设置 \code{nprobe_blocks=1,2,4,8,16}，画出 Recall@10 与延迟曲线，找到召回刚刚接近 1.0 的拐点。

\textbf{更细的负载均衡。}当前 base 按连续区间切分，简单稳定，但没有根据 inverted list 长度、HNSW 图度数或查询热度做动态均衡。如果某些 rank 的局部图搜索持续更慢，可以考虑按随机打散、质心均衡或 list 粒度分配来减小尾部延迟。

\textbf{通信优化。}当前所有候选都 gather 到 rank 0。对于更多 rank，可以改为分层合并：先在节点内合并，再跨节点合并；或者使用 \code{MPI_Reduce} 的自定义 top-$k$ 归约。但在本实验记录中通信/merge 占比很低，因此这不是当前的首要瓶颈。

\section{结论}

本实验完成了 ANN 搜索从单机多线程到 MPI 多进程环境的迁移，并保留 OpenMP 作为 rank 内并行层。IVF-PQ 验证了基础倒排索引迁移；block-HNSW、IVF+HNSW 和 HNSW-on-HNSW 分别覆盖了图索引要求中的 B、A、C 三类方案。双平台全量结果显示，相同参数下 Recall 在 Windows 与鲲鹏上完全一致，说明分布式 top-$k$ 合并逻辑正确；通信与 merge 开销在本验证规模中很小，主要瓶颈仍是本地 ANN 搜索。

从算法效果看，IVF-PQ 与 IVF+HNSW 的召回略低但保持较好的筛选效率；block-HNSW 在三条路径上都达到 Recall@10=1.00000，是当前最可靠的高召回图索引方案；HNSW-on-HNSW 证明了方案 C 的可行性和高召回能力，但全 block 探测配置带来了明显延迟代价。整体来看，本次实现满足了 MPI 划分、混合并行、通信/merge 分析、图索引 A/B/C 和跨平台复现实验的要求。
