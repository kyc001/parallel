# 协程技术调研 15 分钟演讲稿

> 对应 `slides.typ` 当前版本。建议总时长控制在 14 分 30 秒到 15 分 30 秒之间。AI 使用说明已放在 `report.tex` 的正文末尾，课堂展示中不单独占页。

## 1. 封面（约 20 秒）

各位老师、同学好，我是柯云超。今天汇报的题目是“协程技术调研”。我会从并发模型为什么演进到协程讲起，再看它的底层机制、主流语言支持，最后用本机实验回答一个很实际的问题：协程到底擅长什么，又不擅长什么。

## 2. 导览：一个判断，四个问题（约 50 秒）

这次汇报先给出核心判断：协程降低的是“等待”的代价，不是“计算”的代价。很多介绍会说协程很轻量、很快，但如果不区分快在哪里，就容易误用。我的理解是，协程把线程阻塞和回调链，还原成一段可暂停、可恢复的线性代码；代价并没有消失，而是转移到了编译器、运行时和操作系统 I/O 机制里。

后面按四个问题展开：第一，为什么并发模型会一步步演进到协程；第二，协程底层到底保存了什么；第三，各语言为什么分成不同路线；第四，本机实验能说明什么。

## 3. 章节 01：为什么演进到协程（约 10 秒）

先看第一个问题：并发模型为什么会从进程、线程、事件循环，继续走向协程。

## 4. 并发模型演进：让等待越来越便宜（约 55 秒）

这张图展示了一条演进线。多进程隔离性强，但创建和通信成本高；多线程共享内存，写服务端程序更方便，但每个线程都有较重的栈和内核调度成本。当连接数上升到上万级时，如果每个连接都占一个线程，内存和调度压力会很明显。

事件循环把大量 I/O 等待复用到少量线程上，解决了线程数量的问题，但带来了回调地狱：本来线性的业务逻辑被拆成多个回调，异常、局部变量和控制流都不直观。协程可以看作对事件循环的进一步抽象：底层仍然是等待 I/O 事件，表层则恢复为线性代码。每一步都在回答同一个问题：大量“正在等待”的任务，怎样不各自独占昂贵的内核线程。

## 5. 协程不是“快速线程”，而是“便宜的等待”（约 50 秒）

线程模型的问题主要有三个：内存开销、调度开销、阻塞等待。比如传统线程默认栈常常是 MB 级，万级连接会迅速放大内存占用；线程阻塞在 I/O 时，也不能顺手推进其他请求。

协程的解法是把一个并发任务做得更轻：无栈协程通常保存 frame，有栈协程则使用小栈；调度更多发生在用户态；遇到 I/O 或定时器时主动让出执行权。这里要强调，协程不是让 CPU 计算变快，而是让等待期间不浪费线程。

## 6. 章节 02：底层怎么实现（约 10 秒）

接下来进入底层机制。协程真正重要的地方，是它怎样保存状态、怎样恢复执行，以及编译器、运行时和操作系统怎样配合。

## 7. 心智模型：可以中途停下的函数（约 1 分钟）

左边是普通同步函数：调用数据库、调用 RPC，然后返回结果。普通函数一旦调用，就占着当前调用栈一直跑到返回。右边是协程版本，代码看起来几乎一样，但关键区别在 `co_await`：每个 `co_await` 都可能成为挂起点。

挂起时，协程需要保存“下次从哪里继续执行”、当前局部变量，以及必要的运行时信息。之后运行时可以先调度别的任务；等数据库或者 RPC 结果回来，再恢复这个协程。也就是说，协程把手写状态机的负担交给编译器和运行时，让业务代码仍然接近同步写法。

## 8. 两类实现：有栈 vs 无栈（约 1 分 05 秒）

协程实现大体分成两类。有栈协程拥有独立用户态栈，切换时保存栈指针和寄存器，所以可以在较深的调用链中挂起。它对旧同步代码更友好，Go goroutine 和 Java 21 虚拟线程都接近这个方向。代价是要管理栈空间、栈增长，以及运行时调度复杂度。

无栈协程则由编译器把函数改写成状态机，局部变量放进 coroutine frame 里。它的内存通常更小，优化空间也更大，但函数颜色问题更明显：只有 async 或 coroutine 函数能挂起，同步 API 和异步 API 往往会分裂。C++20、Python asyncio、C# async/await、Rust async 都是这条路线。

## 9. 三层协同：编译器 × 运行时 × OS（约 55 秒）

这张图是我认为理解协程最关键的一页。协程不是一个关键字就能完成的。编译器或解释器负责识别 async、await、yield，生成 frame 或状态机；语言运行时负责维护可运行队列、挂起队列、Task/Future、定时器和调度策略；操作系统提供非阻塞 I/O 和多路复用接口，比如 epoll、kqueue、IOCP。

一个典型流程是：协程等待 I/O 时交给运行时，运行时向 OS 等待 fd 就绪；OS 通知就绪后，运行时再把对应协程放回可运行队列。只看语法会低估运行时，只看调度器又会忽略语言层面对错误、取消和资源生命周期的影响。

## 10. 章节 03：各语言如何选型（约 10 秒）

理解底层之后，再看主流语言的取舍。不同语言不是简单地“支持或不支持协程”，而是选择了不同工程路线。

## 11. 主流语言：两条路线（约 1 分 10 秒）

这张表可以概括为两条路线。第一条是 Go 和 Java 21 代表的有栈路线：Go 用 goroutine 和 channel，把调度器内建到语言运行时；Java 21 用虚拟线程，让很多旧的同步代码几乎不用大改就能承载更高并发。

第二条是 C++、Python、C#、Rust 代表的无栈路线。C++20 只给 `co_await` 等底层机制，不给调度器和异步 I/O；Python asyncio 上手快，但事件循环不能被阻塞，并且 CPU 密集任务受 GIL 限制；C# async/await 工程化最成熟；Rust 强调零成本抽象，但运行时要选 tokio 或 async-std，学习成本也更高。

所以选型时不能只问“有没有 async/await”，还要问调度器在哪、阻塞调用谁接管、错误和取消怎么传播。

## 12. Go GMP 调度模型（约 50 秒）

Go 是有栈协程路线的典型例子。G 是 goroutine，M 是操作系统线程，P 是逻辑处理器，持有本地运行队列。运行时把大量 G 映射到较少的 M 上，中间通过 P 做调度。

当某个 P 的本地队列空了，可以从其他 P 偷一半任务，这就是 work stealing。网络 I/O 则通过 netpoller 集成：goroutine 等待网络时会挂起，底层线程可以继续执行别的 goroutine，等 I/O 就绪再恢复。这个模型说明，协程的“轻”离不开运行时调度器。

## 13. 章节 04：实验说明了什么（约 10 秒）

接下来用实验验证前面的判断：协程擅长等待，不擅长凭空加速计算。

## 14. I/O 密集型：协程快 7 到 23 倍（约 1 分 15 秒）

实验设置是 10000 个任务，每个任务 sleep 100ms，用 sleep 模拟网络等待；每项测试重复 5 次，在同一台 i9-13900H 机器上运行。

结果很明显。Python threading 平均 3.13 秒，asyncio 平均 0.446 秒，大约快 7 倍。Java 固定平台线程池平均 5.458 秒，虚拟线程平均 0.235 秒，大约快 23 倍。Go goroutine 平均 0.116 秒，也在很低的量级。

但这里的“快”不是 sleep 被算得更快，而是等待任务没有把内核线程占满。线程池只能让固定数量线程并发等待，剩余任务排队；协程和虚拟线程可以把等待任务挂起，让少量底层线程继续推进其他任务。这正是“等待更便宜”的实验体现。

## 15. CPU 密集 + 切换开销：协程不加速计算（约 1 分 10 秒）

CPU 密集测试用 1000 个任务计算 fib(25)。Python threading 和 asyncio 都比较慢，这主要受 GIL 和解释器执行影响。Go 和 Java 很快，但原因不是协程让 fib 算法变快，而是运行时能把任务分配到多核上执行。

右边是切换开销的量级估计。Python 百万次 yield 大约 2.5 秒，Go 十万次 channel 交互约 122 毫秒，Java 十万个 sleep(0) 任务约 75 毫秒。由于三种操作不完全同构，这里不做精确排名，只看量级。

这一页的结论是：协程切换通常比线程轻，但它不能消除计算本身的指令数。CPU 密集场景优先考虑多线程、多进程、SIMD 或 GPU，而不是把协程当成并行计算工具。

## 16. 内存使用 + 实验局限（约 1 分）

内存实验中，Python asyncio 峰值工作集约 14.1MB，Python threading 约 21.1MB；Go goroutine 显示 106.5MB，Java 虚拟线程约 246MB。这里跨语言不能简单排名，因为 Python、Go、Java 的内存测量口径不同，也包含不同运行时成本。

实验也有局限：I/O 用 sleep 模拟，不涉及真实网络协议栈；fib(25) 只是用来说明协程不自动加速计算；切换测试的操作不完全同构。因此这些数据更适合支撑工程判断，而不是作为绝对性能排名。

## 17. 章节 05：选型决策与总结（约 10 秒）

最后落到工程选型：遇到一个并发问题，怎样判断要不要用协程。

## 18. 三个问题快速判断（约 1 分 10 秒）

我建议用三个问题快速判断。第一，瓶颈是否真的在 I/O 等待？如果瓶颈在 CPU 计算，协程不是优先答案。第二，现有阻塞 API 能不能被运行时接管，或者替换为异步 API？Go 和 Java 21 在这方面迁移成本低；C++、Python、Rust 通常需要显式 async/await，同步库不能随便混进事件循环。

第三，错误、取消和超时能不能结构化管理？协程泄漏、异常传播、资源释放，是工程实践里的真正难点。如果这三个问题都能得到肯定回答，协程通常比传统线程池更适合高并发 I/O；反之，盲目引入 async/await 可能只会增加函数颜色和调试复杂度。

## 19. 三条结论（约 55 秒）

总结三句话。第一，协程的核心价值是用更低的内存和调度开销承载大规模 I/O 并发，它降低的是等待的代价，不是计算的代价。

第二，协程机制需要编译器、语言运行时和操作系统 I/O 多路复用共同完成。只看 async/await 关键字，很容易误解它的成本和能力边界。

第三，语言选型时应关注调度器、取消语义、阻塞调用兼容性和现有生态。Go 和 Java 21 更强调透明迁移，C++、Python、C#、Rust 更强调显式控制，各有适用场景。
