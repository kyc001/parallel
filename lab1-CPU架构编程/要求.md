# Lab1 分析部分相关要求提取（VTune / CPI / 汇编 / profiling 等）

## 1. 报告中“分析部分”的总体要求

### 1.1 实验环境必须说明清楚

实验结果与实验平台密切相关，报告中需要给出完整的软硬件环境，包括：

- CPU 型号
- CPU 核数
- CPU 主频
- 各级 cache 大小
  - L1 cache
  - L2 cache
  - L3 cache
- 内存容量
- 操作系统及版本
- 编译器及版本
- 编译选项
  - 例如 `-O0`
  - `-O2`
  - `-O3`
  - `-march=...`
  - 是否开启调试信息 `-g`
- 若涉及外存或其他系统资源，也需要说明外存型号、容量等信息

特别注意：本实验涉及 cache、超标量、CPI、IPC、汇编等分析，因此 CPU 和 cache 信息必须写清楚。

---

### 1.2 实验设计需要说明

实验设计部分需要说明：

- 测试数据如何生成
  - 可以人为设定固定值
  - 例如矩阵中 `A[i][j] = i + j`
  - 求和数组可以自行生成固定数据
- 问题规模如何设置
  - 应设置多组不同规模
  - 问题规模可以结合 CPU 各级 cache 大小进行设计
  - 例如设置能分别落入 L1 / L2 / L3 cache 或超过 cache 的规模
- 性能指标是什么
  - 运行时间
  - cache hit / miss 情况
  - instructions
  - cycles
  - CPI / IPC
  - 函数级耗时
  - 汇编层面的指令结构
- baseline 是什么
  - 平凡算法 / 原始算法
- 优化算法是什么
  - cache 优化算法
  - 超标量优化算法
  - 循环展开算法
  - 多路链式累加
  - 递归 / 两两归约算法
- 实验想说明什么
  - 例如：优化算法是否更快
  - 问题规模变化是否影响性能
  - cache miss 是否能解释运行时间差异
  - CPI / IPC 是否能解释超标量优化效果
  - 汇编是否能解释编译器优化行为

### 1.4 实验结果分析要求

分析时需要做到“看图说话”，即：

- 描述图表中的实验现象
  - 哪个算法更快
  - 快了多少
  - 性能提升百分比是多少
  - 随问题规模增大，性能如何变化
  - 哪些规模附近出现性能拐点
- 解释实验现象背后的原因
  - 从算法角度解释
  - 从 cache / 访存局部性角度解释
  - 从指令级并行角度解释
  - 从 CPI / IPC 角度解释
  - 从汇编代码角度解释
- 需要将理论分析和 profiling 结果相互印证
  - 例如理论上 cache 优化算法访存局部性更好
  - profiling 中也应看到 cache miss 更少
  - 理论上多路链式累加指令依赖更少
  - profiling 中也应看到 CPI 更低 / IPC 更高
  - 汇编中也应能看到循环展开、SIMD、向量化等优化痕迹

## 2. 矩阵与向量内积实验的分析要求

### 2.1 需要比较的算法

需要实现并比较两种算法：

#### 平凡算法

特点：

- 逐列访问矩阵元素
- 每次外层循环计算出一个完整内积结果
- 与 C/C++ 行主存储方式不匹配
- 空间局部性较差
- 容易导致 cache miss 较多

#### cache 优化算法

特点：

- 改为逐行访问矩阵元素
- 每次外层循环只向多个内积结果累加部分乘法结果
- 与 C/C++ 行主存储方式匹配
- 空间局部性更好
- 理论上 cache miss 更少，性能更好

---

### 2.2 需要分析的问题

报告中应分析：

- 为什么逐列访问 cache 表现较差
- 为什么逐行访问 cache 表现较好
- 两种算法的时间复杂度
- 两种算法的空间复杂度
- 两种算法计算次数是否相近
- 为什么计算次数相近但性能可能差异明显
- 访存开销对程序性能的影响
- 问题规模与 cache 大小之间的关系
- 当数据规模接近或超过某级 cache 时，性能是否发生变化
- 是否可以通过创建额外数组占用内存，观察可用 cache / 内存变化对性能的影响

---

### 2.3 建议使用 profiling 工具分析的指标

可以使用 VTune 或 Perf 获取系统层面指标，包括：

- cache hit 次数
- cache miss 次数
- L1 cache hit / miss
- L2 cache hit / miss
- L3 cache hit / miss
- 缺页次数
- 函数耗时
- 热点函数
- 指令数
- 周期数
- CPI / IPC

需要用这些指标解释：

- 为什么 cache 优化算法更快
- cache miss 是否减少
- cache hit rate 是否提高
- 程序瓶颈是否集中在核心循环
- 不同规模下瓶颈是否变化

---

## 3. n 个数求和实验的分析要求

### 3.1 需要比较的算法

需要实现并比较：

#### 平凡算法 / 链式累加

特点：

- 按顺序逐个累加
- 每一次加法依赖上一次加法结果
- 指令间存在强数据依赖
- 不利于超标量流水线并行执行

#### 超标量优化算法

可以包括：

- 两路链式累加
- 多路链式累加
- 循环展开
- 递归两两相加
- 二重循环实现的归约求和

特点：

- 减少相邻指令间的数据依赖
- 让多条流水线可以并行工作
- 提高指令级并行性
- 理论上 IPC 更高，CPI 更低

---

### 3.2 需要分析的问题

报告中应分析：

- 平凡链式累加为什么存在数据依赖
- 数据依赖如何限制流水线并行
- 两路链式累加为什么可以提升指令级并行性
- 多路累加是否比两路累加更好
- 循环展开如何减少循环控制开销
- 循环展开比例是否公平
- 递归 / 两两归约算法的中间结果如何存储
- 原地存储和辅助数组存储的区别
- 数据访问顺序是否具有空间局部性
- 问题规模如何影响性能
- 问题规模与 cache 大小、流水线数量之间是否有关
- 小规模问题执行时间过短时，是否重复执行核心计算以提高测量精度

---

### 3.3 浮点数结果差异分析

如果使用浮点数求和，还可以分析：

- 平凡算法和优化算法的加法顺序不同
- 浮点数精度有限
- 加法顺序变化可能导致最终结果不同
- 性能优化可能影响数值结果
- 可以比较不同算法的结果误差

## 4. VTune 分析要求

### 4.1 VTune 使用注意事项

- VTune 主要针对 Intel CPU 设计
- 如果使用 AMD 或其他 CPU，VTune 可能无法发挥完整功能
- 非 Intel CPU 建议优先尝试其他性能测试工具，例如 Perf
- VTune 需要以管理员身份运行
- 使用时应尽量关闭病毒防护和防火墙，否则可能无法正常工作

---

### 4.2 VTune 基本分析流程

需要掌握并可在报告中说明：

1. 创建 VTune 项目
2. 进入 `Configure Analysis`
3. 在 `Launch Application` 中选择待测程序
4. 设置程序输入参数
5. 选择分析类型
   - Hotspots
   - Microarchitecture Exploration
   - Parallelism
6. 设置 CPU 采样间隔
7. 运行分析
8. 查看分析结果

---

### 4.3 Hotspots 分析要求

使用 Hotspots 可以观察：

- 总执行时间
- 热点函数
- CPU 使用情况
- 函数调用时间
- Bottom-up 视图
- Caller / Callee 视图
- Top-down Tree
- 平台信息

报告中可以利用 Hotspots 说明：

- 哪些函数最耗时
- 核心计算函数是否为主要瓶颈
- 优化前后热点函数耗时是否下降
- 程序运行时间差异是否与理论预期一致

---

### 4.4 cache 命中率分析要求

分析 cache 时，需要在 Hotspots 中选择：

- `Hardware Event-Based Sampling`

然后添加或勾选硬件事件，例如：

- `MEM_LOAD_RETIRED.L1_HIT`
- `MEM_LOAD_RETIRED.L1_MISS`
- `MEM_LOAD_RETIRED.L2_HIT`
- `MEM_LOAD_RETIRED.L2_MISS`
- `MEM_LOAD_RETIRED.L3_HIT`
- `MEM_LOAD_RETIRED.L3_MISS`

需要比较：

- 平凡算法的 L1 / L2 / L3 hit 次数
- 平凡算法的 L1 / L2 / L3 miss 次数
- cache 优化算法的 L1 / L2 / L3 hit 次数
- cache 优化算法的 L1 / L2 / L3 miss 次数
- 优化前后 cache miss 是否减少
- 优化前后 cache hit rate 是否提高

分析结论应说明：

- 按列访问为什么 cache miss 较多
- 按行访问为什么 cache miss 较少
- cache miss 的减少是否能解释运行时间下降

---

### 4.5 Microarchitecture Exploration 分析要求

分析超标量和 CPI / IPC 时，应使用：

- `Microarchitecture Exploration`

需要关注 Summary 中的数据：

- `Clockticks`
  - 总周期数
- `Instructions Retired`
  - 执行完成的指令数
- `CPI`
  - 每条指令平均消耗周期数
- 或由 CPI 推出 IPC
  - `IPC = 1 / CPI`

需要进入 Bottom-up 查看：

- 每个函数的 CPU 时间
- 每个函数的周期数
- 每个函数的指令数
- 每个函数的 CPI
- 核心函数的性能表现

注意：

- 使用 gcc 编译时应加 `-g`
- `-g` 用于保留调试信息，方便 VTune 对应到源代码和函数

---

### 4.6 CPI / IPC 分析要求

需要重点比较：

- 链式累加算法的 instructions
- 链式累加算法的 cycles
- 链式累加算法的 CPI / IPC
- 两路链式累加算法的 instructions
- 两路链式累加算法的 cycles
- 两路链式累加算法的 CPI / IPC

分析时应说明：

- 两种算法的指令数大致相同或相近
- 两路链式累加的周期数更少
- 两路链式累加 CPI 更低
- 两路链式累加 IPC 更高
- 这说明其更好地利用了 CPU 超标量架构
- 原因是两条累加链之间依赖较少，可以让多条流水线并行执行

---

### 4.7 VTune 源代码和汇编级分析要求

VTune 不仅可以查看函数级性能，还可以查看：

- 每段源代码的执行情况
- 每段代码的执行次数
- 每段代码的周期数
- 每段代码对应的汇编代码
- 每条汇编指令附近的性能事件
- cache miss 在具体代码 / 指令上的分布

报告中可以进一步分析：

- 核心循环对应哪些汇编指令
- 哪些指令消耗周期较多
- 哪些指令附近 cache miss 较多
- 编译器是否进行了循环展开
- 编译器是否进行了向量化
- 优化算法的汇编是否体现出更高的并行性

## 5. Perf 分析要求

如果使用 Linux，也可以使用 Perf 进行性能剖析。

### 5.1 Perf 安装与环境要求

Ubuntu 下可以安装：

```bash
sudo apt install linux-tools-$(uname -r) linux-tools-generic
````

注意：

* 如果 Linux 运行在虚拟机中，需要开启虚拟化 CPU 性能计数器或虚拟化 PMU
* VirtualBox、WSL2 可能不支持类似功能
* 硬件事件采样依赖 PMU

---

### 5.2 Perf 事件查看

可以使用：

```bash
perf list -h
perf list hw
perf list cache
perf list pmu
perf list l2_cache
perf list pmu | grep cache
```

用于查看系统支持哪些性能事件。

---

### 5.3 Perf 的两种模式

Perf 有两类主要使用方式：

#### Counting 模式

例如：

```bash
perf stat
```

作用：

* 统计某段时间内某事件发生的总次数

常用于统计：

* instructions
* cycles
* cache misses
* cache references
* branches
* branch misses

#### Sampling 模式

例如：

```bash
perf record
perf report
```

作用：

* 按采样方式记录程序运行信息
* 可查看热点函数
* 可查看函数调用关系
* 可查看反汇编与源码注释

---

### 5.4 Perf cache 分析要求

针对 cache，可以使用类似命令：

```bash
gcc column_sum.c -g -o column_sum

perf record -e L1-dcache-load-misses,L1-dcache-loads,L1-dcache-stores -ag ./row_column

perf report
```

需要分析：

* L1-dcache-load-misses
* L1-dcache-loads
* L1-dcache-stores
* 各函数在 cache miss 事件中的占比
* `col_major` 和 `row_major` 的 cache miss 差异
* 哪个函数是主要瓶颈

在 `perf report` 中可以进一步：

* 进入具体函数
* 选择 `Annotate`
* 查看带源码注释的反汇编代码
* 查看每条指令上的事件采样比例

---

### 5.5 Perf CPI / IPC 分析要求

可使用：

```bash
perf stat -e instructions,cycles -r 100 ./program
```

需要记录：

* instructions
* cycles
* seconds time elapsed
* IPC
* CPI

其中：

```text
IPC = instructions / cycles
CPI = cycles / instructions
```

需要比较：

* 平凡链式累加算法
* 两路展开累加算法
* 多路展开累加算法，如果实现了
* 递归 / 归约算法，如果实现了

分析重点：

* 优化算法 instructions 是否与平凡算法接近
* 优化算法 cycles 是否明显减少
* 优化算法 IPC 是否更高
* 优化算法 CPI 是否更低
* 这些结果是否证明优化算法更好地利用了超标量架构

---

### 5.6 Perf record 详细分析要求

也可以使用：

```bash
perf record
perf report
```

分别收集：

* instruction 事件
* cycle 事件

然后计算或分析：

* 函数级 CPI
* 热点函数
* 热点指令
* 汇编层面的性能瓶颈

---

### 5.7 可视化分析

可以进一步使用：

* 火焰图
* hotspot 工具
* VTune 导入 perf.data

报告中可展示：

* 火焰图
* 函数调用关系
* 瓶颈函数宽度
* 不同事件下的热点位置

## 6. Godbolt 汇编分析要求

### 6.1 Godbolt 的作用

Godbolt 是在线编译浏览器，可以用于：

* 输入 C / C++ 源代码
* 选择编译器
* 查看生成的汇编代码
* 分析源代码与汇编代码的对应关系
* 比较不同算法生成的汇编差异
* 比较不同编译选项生成的汇编差异

---

### 6.2 需要进行的汇编分析

报告中可以使用 Godbolt 分析：

* 平凡链式累加算法的汇编
* 两路链式累加算法的汇编
* 多路累加算法的汇编
* 递归 / 归约算法的汇编
* cache 优化前后的矩阵访问代码汇编
* 不同优化等级下的汇编

建议比较：

* 无优化编译结果
* `-O0`
* `-O2`
* `-O3`
* `-march=skylake-avx512`
* 其他与本机 CPU 对应的 `-march` 选项

---

### 6.3 需要关注的汇编现象

分析汇编时需要关注：

* 核心循环是否被展开
* 是否出现 SIMD 指令
* 是否出现 SSE / AVX / AVX2 / AVX512 指令
* 是否进行了自动向量化
* 循环控制指令是否减少
* load / store 指令数量是否变化
* 加法指令之间是否存在明显依赖链
* 多路累加是否生成多个独立累加寄存器
* 优化后的汇编是否能解释 CPI / IPC 的改善
* 编译器优化是否改变了核心循环结构

---

### 6.4 Godbolt 使用技巧

Godbolt 中可以：

* 通过颜色对应查看源代码与汇编代码的关系
* 将鼠标悬停在汇编指令上查看指令解释
* 右键选择 `View assembly documentation` 查看更详细的指令文档
* 修改编译选项后观察汇编变化

报告中可以截图或摘录关键汇编片段，但应重点解释：

* 这段汇编对应哪段源代码
* 它体现了什么优化
* 它如何影响性能
* 它与 VTune / Perf 的 CPI、IPC、cycles 结果是否一致

## 7. 最终分析部分建议结构

报告中的“实验结果分析 / profiling 分析”部分可以按如下结构组织：

### 7.1 运行时间分析

* 展示不同问题规模下的运行时间
* 比较平凡算法和优化算法
* 计算加速比
* 描述性能变化趋势

### 7.2 cache 行为分析

* 使用 VTune 或 Perf 收集 cache 事件
* 比较 L1 / L2 / L3 cache hit / miss
* 分析 cache miss 与运行时间之间的关系
* 解释按行访问和按列访问的性能差异

### 7.3 超标量与 CPI / IPC 分析

* 使用 VTune Microarchitecture Exploration 或 Perf stat
* 记录 instructions、cycles、CPI、IPC
* 比较链式累加和多路累加
* 说明 CPI 降低 / IPC 提高的原因
* 从指令依赖和流水线并行角度解释

### 7.4 汇编代码分析

* 使用 Godbolt 或 VTune / Perf Annotate 查看汇编
* 比较不同算法的汇编
* 比较不同编译优化选项的汇编
* 分析是否有循环展开、SIMD、自动向量化
* 用汇编解释性能差异

### 7.5 理论与实验对应

* 将算法理论分析与实验结果对应
* 将 cache 分析与运行时间对应
* 将 CPI / IPC 分析与超标量理论对应
* 将汇编分析与编译器优化对应
* 说明实验现象是否符合预期
* 如果不符合，需要分析可能原因
